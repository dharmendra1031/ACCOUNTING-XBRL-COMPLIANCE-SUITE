## UI acceptance
Compact form fields, 1 scroll owner, no wasted vertical space, 2 columns for ordinary desktop masters, bounded server-side grids, visible authorized actions and totals. Long forms may scroll where necessary; never clip access, error messages or 200% zoom content. Every screen needs its own route, edition, permission, states, validation, toolbar, reusable components, responsive RTL behavior and screenshot/evidence gate. Master form at 1366x768 should not scroll for no reason. Do not construct native POS until separately approved.

## Compact UI baseline
Appendix I – Compact Enterprise UI/UX and No-Unnecessary-Scrolling Contract (19 November 2026)
STATUS: Proposed implementation baseline for UX/Product approval, not completed UI or a promise of zero scrolling. Applies to SCR-001–038, accounting forms, reports and approved edition-specific workflows. Existing design-system reuse is preferred; precise colors, fonts and POS reference styling remain subject to approved design files. No duplicate screen/component or feature is authorized by this appendix.
I-01 Information density without clutter. Desktop screens should be compact, aligned and readable, not waste vertical space on huge headings, cards, whitespace, repeated labels or redundant actions. A standard workspace uses one persistent header showing company, branch and period where relevant; a permission-scoped side navigation; a compact page title/toolbar; one content region; and a consistent primary action area. Do not repeat tenant/company context as separate full-height form cards when already fixed in the header.
I-02 Desktop viewport baseline. Design and manually test at 1366×768 at 100% browser zoom, 1440×900 and 1920×1080; also 125%/200% zoom and smaller tablet/mobile widths. On a typical edit form with up to 8 primary fields, no optional sections expanded and normal validation state, aim to show the title, required fields and Save/Cancel without avoidable whole-page vertical scrolling at 1366×768. Do not force a zero-scroll rule if content, text scaling, keyboard visibility or screen size genuinely requires scrolling; never clip actions, errors, legal notes or audit information.
I-03 Layout sizing as starting tokens, not copied hardcoded pixels. Suggested desktop shell: global top bar 56–60px high, navigation 216–240px wide if expanded, compact page heading and toolbar 44–56px; main content padding 12–20px; field/row gap 8–12px; section gap 12–16px; normal input/select height 36–40px; dense data row height 36–44px; mobile tap targets approximately 44px with adequate spacing. Keep tokens centralized (e.g., --header-height, --nav-width, --field-height, --space-2) and adjust after usability testing. No bespoke heights for each page without a demonstrated need.
I-04 Form composition. On desktop, ordinary master forms use a sensible two-column grid with aligned top labels and grouped related fields; one-column for complex narrative/money line editors and mobile; do not use three-plus columns when it damages comprehension or accessibility. Required fields and blockers appear before optional ones. Use progressive disclosure for uncommon advanced settings and audit details, not to conceal mandatory inputs. Keep only one Save/Cancel action group per workflow; edit/create can share a permission-scoped component, while posted history remains read-only. Prefer inline validation and lightweight banners over tall modal stacks.
I-05 Scroll ownership. Prefer one primary vertical scroll container per workspace, with sticky/fixed header and action toolbar when appropriate. A short form or small list should not scroll solely because an oversized header/footer/card consumes the viewport. Avoid nested vertical scrollbars (page + drawer + modal + table); when a long table must scroll, select one well-defined grid body scroll area with a sticky table header and bounded height, and ensure keyboard focus/scroll-to-error work. Wide financial columns may use an explicit horizontal grid scroll with frozen identifier/total columns as required; preserve access to all columns and visible horizontal scroll cues. Full-page scroll is acceptable for genuinely long forms, accessible zoom, disclosure text and mobile, but never hide the save button or validation summary beneath a clipped viewport.
I-06 Table density and very large data. Lists run server-side filtering, sorting and bounded pagination or keyset cursor, with 25/50 as suggested default page options and virtual rows only if profiling shows benefits. Do not render thousands of journal/invoice/stock rows in DOM. Show concise totals, status, currency, last update and quick filters in one compact toolbar; search with debounce; stable column widths, numeric right alignment, KWD 3-decimal display, timestamps and read-only/drilldown affordances. Reuse one table/filters/empty-loading-error framework for SCR-020/038 reports, SCR-024 journals, SCR-029 stock and approvals. Never compute finance aggregates only in the browser.
I-07 High-risk finance flows. Journal entry SCR-005 shows voucher identity, posting date/period/status, compact debit/credit lines with a persistent balanced difference footer and Save Draft / Submit / Post actions only when authorized. Invoice and bill workspaces show line items, amounts, discounts/tax only where applicable and customer/supplier; avoid separate giant cards for each field. Pending approval, Posted, Locked and Reversed are visibly different; post/approve actions require server-confirmed result and exact next step; no duplicate Post buttons in list and detail that can bypass idempotency. Inline errors scroll/focus to the exact field without shifting the whole page unnecessarily.
I-08 Responsive behavior. At tablet widths collapse navigation into a usable drawer and change two-column forms to one where needed. On mobile, long accounting tables become a dedicated horizontally scrollable grid or limited detail/card view without dropping regulatory-critical columns or mislabeling totals. RTL must reverse navigation and reading order appropriately without reversing LTR codes, transaction IDs, dates or numeric semantics. Browser 200% zoom, keyboard-only operation, visible focus, screen reader labelling, error association, adequate contrast and touch accessibility remain mandatory. Compact must never mean microscopic labels or inaccessible 28px actions.
I-09 Dialogs and forms of mixed length. Prefer side panels/drawers for concise create/edit actions where there is enough viewport; use full-page editor for journals, invoices, bulk imports and large reconciliations. If a dialog exceeds available screen height, allow one internal scrollable content region with fixed visible heading and actions and focus trap; avoid scroll within scroll. Unsaved-change warning appears before context switch, route change or closing an edited dialog. No unnecessary approval step or repeated confirmation for reversible draft edits; confirm truly irreversible posting/finalization.
I-10 Shared component contract and code discipline. Shared reusable components: AppShell, CompanyContextSwitcher, PageHeaderToolbar, PermissionGate, FormField, MoneyInput, DatePeriodPicker, ValidationSummary, SmartDataGrid, StatusBadge, ApprovalActionBar, ConfirmDialog, ReportFilterPanel, EmptyErrorLoadingState. Implement only components required by approved screens; one shared component should not carry irrelevant props or alternate duplicated business logic. Organize CSS design tokens centrally; avoid per-page copied layout, ad-hoc !important, global fixed heights, dead code, duplicate API calls, uncontrolled cache state and pointless abstractions. No native POS screen until DEC-007 approves it; approved Ibdaa Tailor POS reference must be inspected separately before copying exact POS sizing.
I-11 Accessibility and performance balance. UI interactive readiness includes visible real data or an explicit loading/error state; use skeletons only when helpful. Prevent waterfall fetches, cancel stale requests on company/branch/period switch and preserve form draft deliberately. Control layout shift when validation appears; do not freeze page or mask server errors for speed. Measure page-height overflow, cumulative layout shift, API/render p95 and table memory on representative data. Browser layout at a single screenshot size cannot prove mobile, keyboard and zoom behavior.
I-12 Screen-specific acceptance before code. For each SCR ID, record screen category (dashboard/list/form/workbench/report/read-only), fields/conditional visibility, primary/secondary actions, single-scroll owner, desktop and mobile wireframe, approval dependency, reusable components, permission and performance/UX tests. Explicitly mark Not Applicable for draft/save states on login or immutable reports where unsupported. Avoid duplicating SCR-017 and SCR-033 approval inboxes, SCR-018 and SCR-037 filing details or SCR-020 and SCR-038 report filter UI; reuse services/components where the security workflow allows.
I-13 Design exit test. At 1366×768 100%, review at least Login, Company Setup, COA, Journal, Sales Invoice, Purchase Invoice, Bank Reconciliation, Reports, Filing Preview and Approval Inbox. A typical short form should not create gratuitous page scrolling; large tables should scroll in the intended single container without losing context. Verify 125% and 200% zoom, 320/375px mobile, EN/AR RTL, a realistic validation-error state, long Arabic labels and 1,000+ result search with API pagination.
