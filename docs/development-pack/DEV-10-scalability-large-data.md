## Central architectural commitment
Start with one modular ASP.NET Core API and SQL Server OLTP, an approved existing UI framework, one authoritative posting engine. Do not prematurely add 14 independent microservices, duplicate database services, speculative queues/caches, sharding or separate country deployments. Developer productivity and audit correctness are first-class performance requirements. Jobs, cache, read models and scale-out follow measured profiling.

## Full architecture and benchmark requirements
Appendix H – Scalable, Fast and Maintainable Architecture: Implementation Contract
STATUS: Proposed engineering baseline for approval and performance testing; NOT measured speed or committed infrastructure SLA. Architecture choices follow TECH-01: ASP.NET Core modular monolith + SQL Server, one authoritative posting service, one deployed web API initially; frontend remains D-01 OPEN. Scale out API and workers only once measured. Avoid microservices, CQRS duplication, data warehouse, sharding or multiple queues without justified bottleneck.
H.1 Service boundaries and maintainability
Keep one deployable API with cohesive domain modules: Identity/Organization, Accounting, Receivables/Payables, Inventory, Banking, Reporting, XBRL/Regulatory. Modules expose explicit use-case interfaces but reuse shared auth, posting, audit, validation and persistence infrastructure. Apply dependency direction UI/API→application use cases→domain policies→persistence/integrations. Avoid duplicated business logic in controllers, React components, SQL triggers and background workers. Prefer small feature-oriented files and readable tests over premature layers and generic repositories. Version APIs and DB migrations; enforce review/code style/static analysis and stable interfaces. Introduce asynchronous worker process only for genuinely long imports, exports, validation and notifications; persistent job state in DB with resumability.
H.2 Data scale and relational model
SQL Server is authoritative for financial data; use narrow, typed, indexed tenant/company keys and SQL DECIMAL with approved scale, UTC timestamps, rowversion/optimistic concurrency and immutable posted journal references. Ensure exact tenant/company/branch scoped foreign keys, filtered permissions and a unique canonical event key per posting. Start with normal indexed rowstore OLTP tables, normalize source documents and ledger lines, and use migrations with rollback/forward plan. Design unique keys for invoice numbers, source events, role grants and financial posting. Every critical access path must be indexed based on measured WHERE/JOIN/ORDER BY patterns, typically (TenantId,CompanyId,PostingDate,stable Line/JournalId), (CompanyId,AccountId,PostingDate,Id), (CompanyId,Status,DueDate,Id), (CompanyId,SourceSystem,EventType,SourceEventId), plus targeted covering indexes. Validate index order/selectivity and write amplification using actual SQL plans: these are candidate shapes, not mandated redundant indexes. NEVER create an index blindly for every column, partition by tenant by default or build separate databases for every company. SQL partitioning/columnstore only when benchmarked range scans, archival or analytical workloads materially benefit; it may make OLTP slower.
H.3 API/read and write paths
All list endpoints are server-filtered and limit columns, sorting and page size; return a default 50 rows and a maximum 200 rows unless a specific workflow is approved. Prefer stable keyset/cursor pagination for deep journal/customer/stock history; avoid unbounded OFFSET and SELECT *. Use read-only EF Core projections/AsNoTracking where appropriate; prevent N+1 queries and cartesian explosion. Never pull large tables into memory to filter; aggregate in SQL using bounded parameters. Use async I/O end to end, cancellation tokens, bounded timeouts, resource/connection pooling and idempotent command retry. Critical Posting transaction locks only necessary rows, validates period and balanced journal, atomically updates source status/unique posting and audit, then commits. Retry and concurrent posting cannot produce a second journal. Never hold DB transaction open during external API/file I/O; use reliable post-commit work scheduling/outbox ONLY if evidence of lost jobs requires it. Every write returns committed reference, version and correlation ID, not optimistic UI success.
H.4 Fast UI and correct caching
Frontend must be approved and reused from existing components where suitable. Lazy-load modules/routes, virtualize large tables, debounce search, cancel obsolete requests on company/period switch, use server-side filters and explicit loading/empty/failed states. Keep only bounded result pages in browser memory. Currency, date, Arabic RTL and accessible form states must not trigger full-table refetch. Cache static master choices/taxonomy metadata and approved immutable report snapshots only with tenant+company+scope+period+permission+version-aware cache keys. Live balances, approval state, period locks and filing status require authoritative read or safe version-checked short-lived cache with invalidation on posting, approval, role change, snapshot/version change; never share cross-tenant responses. Add distributed cache only after multiple API instances and measured cache benefit, not as a default dependency.
H.5 Reporting, jobs, XBRL and bulk flows
Small reports use indexed, server-aggregated queries. Heavy TB, balance sheet, period reports, 58 report exports, large reconciliations and XBRL taxonomy/validation must run as cancellable, durable, permission-scoped async jobs with 202 + status/progress, retry budgets and bounded concurrency where they exceed interactive latency. Generate immutable report snapshots only from defined ledger cutoff and approved mapping; store lineage and invalidate/reissue on approved ledger changes. Stream CSV/export and files using chunking, enforce role, row/time/file-size limits and object-storage lifecycle. Reject/queue imports over agreed limits; import staging validates schema, currencies, duplicates and totals before atomic financial publication. Never calculate each dashboard by rescanning all journal lines for every user request; add period/account summary/read models only where performance profiling shows need and reconcile them against GL. Keep authoritative balance/inventory correctness ahead of stale dashboard speed.
H.6 Representative benchmark envelope — PROPOSAL, NOT A CLAIM
At kickoff, Product and Ops must approve tenant counts, skew, report period, DB storage, load tool, hardware and acceptable cloud budget. Example stress fixtures to prepare: Level A = 10 million posted journal lines, 1 million invoices, 2 million stock movements, 100 concurrently active user sessions; Level B = 100 million posted journal lines, 10 million invoices, 20 million stock movements, 500 concurrently active sessions, a largest tenant holding 40% of records; Level C = >= 500 million journal lines and 1,000 concurrent sessions as capacity-planning/re-architecture trigger rather than a Phase-1 commitment. Include a realistic mixture of writes, account-lookup, dashboards, AR/AP ageing, journal search, month-end, large export, integration retries, Arabic RTL and permissions. Clearly separate generated DB volume, active concurrent sessions and actual request throughput. Re-run with cold cache, hot cache, newest/oldest periods, skewed companies and read/write contention.
H.7 Proposed measurable SLOs — require signed capacity/infra budget
At Level A fixture on agreed production-like infrastructure, proposed targets: interactive navigation/data-ready p95 ≤ 3.0 s (at browser, excluding user think time, including real API and render); common indexed GET/list APIs p95 ≤ 400 ms, p99 ≤ 1.2 s; posting command p95 ≤ 1.5 s, p99 ≤ 3.0 s under contention without financial invariant failure; paginated history search p95 ≤ 800 ms; simple dashboard p95 ≤ 1.5 s with disclosed freshness. Large reports/exports are **queued**, not falsely assigned interactive response time; the UI must return job acknowledgment p95 ≤ 500 ms and show progress, with report completion budget separately approved per dataset size. Error/timeout/rate-limit budgets, request mixes, load ramp and warmup must be documented. Levels B/C are separate capacity-gate benchmarks with no pre-claimed threshold. Section 15's 99.5% monthly availability is a proposed SLA target requiring definition of exclusions, monitoring and operator readiness. p95/p99 are not guarantees until load tests pass.
H.8 Observability and regression gates
Instrument API request latency by route, SQL command duration and plan regressions, DB CPU/IO/waits/locks/deadlocks, row count/index growth, connection pool saturation, GC/memory, job queue lag, cache hit/miss, report age, integration retry and errors. Use structured logs and correlation/trace IDs with sensitive fields redacted. Enforce performance budget regressions in a dedicated scheduled/staging test with representative anonymized/synthetic datasets, not in every tiny unit-test CI run. Collect query execution plans and Query Store baselines for top account/journal/AR/AP/stock/report queries; investigate lock contention and N+1 before adding infrastructure. Monitor data skew and daily/weekly growth; test restore/roll-forward with large ledgers. After every architectural optimization rerun accuracy, tenant-scope and idempotency regression tests.
H.9 Escalation choices only when measured
First optimize algorithm, query projection, indexes and transaction duration; next add targeted immutable-snapshot caching and asynchronous jobs; then horizontally scale stateless API workers or tune DB resources; only finally consider separate analytic read model/columnstore, partitioning or independently managed services when justified by measured Level B/C bottlenecks and operational cost. Do not denormalize financial source-of-truth or sacrifice auditability to win a benchmark.
H.10 Release gate
A release is performance-ready only if the approved load envelope has recorded infrastructure specs, target SLOs, p95/p99 results, throughput, error rate, DB plans, memory/CPU growth, functional ledger reconciliation, no tenant data leakage, job recovery and RPO/RTO evidence; incidents or threshold misses are tracked as blocking defects or explicit owner-approved scoped waivers. A scaffold build/health endpoint is NOT evidence this software is fast with large data.
Additional scalability acceptance tests (specified, not yet run):
TC-081: Level A/B deep journal pagination stays bounded, stable and permission-scoped without whole-table reads; no duplicates/missing records at equal timestamps.
TC-082: Load test with 100M posting rows and skewed tenant shows recorded p95/p99, DB wait/lock/memory metrics and no financial invariants violated (threshold Level B requires approval).
TC-083: Concurrent posting of the same source event causes exactly one journal; other concurrent unrelated accounts proceed without global lock serialization.
TC-084: Dashboard snapshot/cache invalidates on posting, period reopen, role revoke and company switch; no stale approved-as-live figure or cross-tenant leak.
TC-085: Import/export of million-row synthetic dataset streams/chunks with bounded memory and resilient async state, enforced caps and scoped access.
TC-086: Large month-close/report workloads preserve cutoff, GL tie-out, job retry and cancellation; no partial approved output after failure.
TC-087: User-perceived p95 screen readiness includes API/render and Arabic RTL at approved representative dataset and device/network profiles.
TC-088: SQL Query Store/plans for top queries identify regression after index or schema migration; performance failure blocks release.
TC-089: Cold-cache, high-cardinality company and oldest-period query coverage demonstrates stable bounded queries, no N+1, and correct page ordering.
TC-090: Database restore and application restart with queued work preserve source event uniqueness, report lineage, audit and tenant isolation within approved capacity/RPO/RTO.

## Cross-document review corrections — 2026-11-19

**Durability vs simplicity:** A single modular API + SQL Server stays the baseline. When committed financial work implies follow-up jobs, an in-transaction durable job record or demonstrably equivalent persisted handoff is required; do not rely on `Task.Run`, in-memory queues or a best-effort post-commit publish. Implement the lightest proven persistence/worker arrangement; avoid generic distributed brokers/outbox systems until a real external-delivery need exists. In-memory optimization must NEVER duplicate or lose financial recognition.

**Performance budget is measurable, not a guarantee:** 10M rows/100 sessions and 100M rows/500 sessions describe proposed synthetic capacity tests. Explicitly record hardware, storage, indexing, tenants and largest-tenant skew, cold/hot cache, document age, query mix, concurrency and write-to-read ratio. API p95 is measured server-side, data-ready p95 at browser, background job completion separately from 202 acknowledgment. Do not promise 400ms GET or 1.5s posting at unspecified cloud cost or Level B before test evidence.

**Bottleneck ladder:** Inspect SQL Query Store, actual execution plans, scans, sort spills, lock waits, indexes and transaction duration first; then consider targeted scoped cache/approved snapshots, bounded async jobs or more stateless API instances, and finally optional columnstore/partitioning/analytics only after measured evidence. Keep mutable GL records authoritative and immutable posted references. Recheck permission + as-of data freshness under concurrency after every performance optimization; track TC-081–090 and TC-091–102 without claiming they pass.

**Frontend large-data constraint:** Thousands of transactions are paginated/virtualized using server-side scoped filters, deterministic tie-breaker keys and bounded DOM memory; compact forms must remain keyboard and 200%-zoom accessible rather than forcing fake zero-scroll layouts. See SRS J-06/J-12.
